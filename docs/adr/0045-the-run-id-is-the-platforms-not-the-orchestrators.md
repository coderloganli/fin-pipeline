# The run identifier belongs to the platform; the orchestrator's is recorded beside it

summary: The pipeline run id keeps the `YYYYMMDDTHHMMSSZ-xxxxxx` shape `docs/adr/0019`
fixed and is generated by whoever starts the run; Airflow's own run id is recorded as a
field on the `started` event, so neither identity has to become the other.

## Context

`ingest.load` generates a run identifier and stamps it on every raw row it writes
(`docs/adr/0018`), and the lineage chain this platform is built on — a figure, to the
rows behind it, to the run that landed them — is that identifier followed backwards.

An orchestrator arrives carrying an identifier of its own. Every DAG run has one, it is
what the UI is indexed by, and it is what somebody looking at a failed run is holding.
So there are now two candidate answers to "which run produced this number", and
`record-every-pipeline-run` deliberately left the choice to this ticket rather than
guessing at it.

Three shapes were available: adopt Airflow's identifier as the platform's, keep the
platform's and ignore Airflow's, or keep one and record the other.

## Decision

The pipeline run id is the platform's own, in the shape `docs/adr/0019` fixed, and it is
what `docs/adr/0018` stamps on rows. It is generated by whatever starts the run — the
runner when a DAG starts one, `ingest.load` when somebody types it directly.

The orchestrator's identity is recorded as two fields on the `started` event:

    {"event": "started", "run_id": R, "orchestrator": "airflow",
     "orchestrator_run_id": "manual__2026-09-08T03:00:00+00:00", ...}

Both are absent when nothing orchestrated the run. `python -m ingest.runs --run <id>`
prints them when they are there.

## Reasoning

Adopting Airflow's identifier was the tempting one, because one identifier is simpler
than two. It fails on the runs that have no orchestrator. A load typed by hand while
investigating something still writes rows, and those rows still need an identifier; the
platform would have to generate one anyway, and would then have two formats in the same
column, one of them sorting differently from the other. `docs/adr/0019` chose its format
so that a log orders to the second by eye, and a column holding two formats does not.

It also inverts a dependency that should not be inverted. The identifier on a raw row is
a fact about the warehouse, and making it a foreign key into a scheduler's metadata
database means the provenance of the data cannot be interpreted without that scheduler
still existing, still holding that run, and still being the scheduler in use. Orchestrators
get replaced. Ledger rows from 2026 do not.

Ignoring Airflow's identifier entirely was rejected for the opposite reason: it is what
the person with the problem is actually holding. They are looking at a red task in a UI,
and the question is which run record to read. One field answers it, in the direction it
is asked, and the reverse direction — record to UI — is the same field read the other
way.

Recording it on the `started` event rather than on every step follows `docs/adr/0020`:
facts about a run live on the run, not repeated on the things underneath it.

One consequence has to be stated because it shaped `docs/adr/0044`. A DAG run keeps one
pipeline run id across the retry of an individual task, because `open_run` is its own
task and the identifier reaches the others through XCom. So a retried step really does
start twice under one run id, and the record has to be able to say so. That is why
`docs/adr/0044` folds a second `step_started` after a finished attempt as a retry rather
than raising — the alternative was to give each retry a run id of its own, which would
scatter one night across several records and defeat the reason for having them.
